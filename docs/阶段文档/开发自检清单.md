# 开发自检清单（每版开发与验收前必过）

> 来源：v0.7～v0.9 三轮独立复核反复暴露同类问题的复盘。本文是给 AI（DeepSeek/我）的固定自检项，产品经理无需读。每次开发、每次写校验/迁移/状态逻辑前，先过一遍。

## 一、schema 加字段 = 三件套（最高优先级）

凡新增存档字段（schema 升版）必须**同时**完成三件事，缺一不可：

1. **旧版本迁移补默认**：`migrateSave`/`normalizeSave` 对 v1～N-1 旧档补安全默认值，且用「字段引入版本常量」判断，不得用 `SCHEMA_VERSION` 动态比较（v0.8 曾因 `schemaVersion < SCHEMA_VERSION` 回归放行 v6 坏档）。
2. **当前版本缺字段拒绝**：`importSave` 校验里，当前版本缺该字段 → `ok:false`；只有「真正没有该字段的旧版本」才允许缺。
3. **字段间一致性校验**：新字段彼此（及与已有字段）的关系要校验，如「当日次数 ↔ 当日记录 ↔ 日期标记」必须一致。

并且：**校验不得只信任文件自报的版本号**——即使文件自称旧版本，只要携带了新版本字段，就必须按新版本规则校验（v0.9 最终复核的「降版本绕过」就是漏了这条）。

## 二、每个校验函数配「成对失败用例」

写 `validateXxx` 时，同时写两组测试：
- 合法档可过；
- 该被拒的坏档（缺字段、非法值、字段间矛盾、越界、负资源）返回 `ok:false` 且不覆盖现档。

不写失败用例，不算完成。历次独立复核补的几乎都是「坏档应拒绝」这一半。

## 三、实现前把 PRD 条款逐句抄进验收列

每个版本的 PRD 都有「必须看到 / 必须拒绝 / 不触发」三类句子。开发文档的「验收」节要**逐句抄录**，实现后逐条打勾。历次漏掉的（切换前后对比、修仙录记录、图鉴首次记录、回执分列、显示精度、秘境卡信息）都写在 PRD 里，但不在主链路上，所以没做。

## 四、状态类改动统一来源

显示、预估、操作必须读**同一个结算态**，禁止 `state`（原始）与 `view`（结算）混用。跨日/跨天重置场景尤其要检查（v0.8、v0.9 的「按钮可点但操作被旧状态拦回」）。

## 五、并发/高价值事务不写「沿用旧机制」，必须实测

双标签同日竞争、扣费、晋级、领奖这类「只许成功一次」的事务：
- 有单测（CAS/每日限次）；
- 浏览器双标签实测一次；
- 不能只写「沿用 v0.x 机制」代替。

## 六、交付前必跑四条命令 + 逐项核对

```bash
npm run typecheck   # 必须为 0 报错
npm test            # 全绿
npm run build       # 通过
# 后端：.venv/bin/python -m pytest -q
```

并且：新增测试用了新类型/新导入时，**确认 import 已补**（v0.9 最终复核的 typecheck 失败就是测试文件漏 import）。

## 七、文档状态同步

PRD 标题/导语/结尾的「待审阅/尚未开发」要在确认/开发/复核后同步改掉，README 的版本状态与测试数量同步，`docs/项目状态.md` 的「上次停在/验收与待办/阶段历史」逐轮更新。

---

> 执行方式：每进入一个新版本（v1.0 及之后），开发前先把本文读一遍，按顺序过完再动手；每交付一个阶段，对照本文逐条自查后再声称完成。
