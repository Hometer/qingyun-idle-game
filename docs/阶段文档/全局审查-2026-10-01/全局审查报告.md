## 2. P1：应先修复的阻塞问题

### P1-01 正常游戏操作产生的存档无法导回

**已通过确定性引擎复现三种独立路径。**

1. 筑基角色炼制凡品养元丹后导出，再原样导入，返回“库存装备无效”。库存校验漏掉 `yangYuanDan_*`、`juLingDan_*`；服完丹后残留零数量键也会被拒绝。
2. 风共鸣启动 30 分钟闭关，合法结束时间为 29 分钟；原样导入返回“长期任务起止时间与时长不符”。启动逻辑缩短耗时，校验却固定按原时长核算。60/120 分钟的同类风险为 58/116 分钟；任务还缺锁定共鸣/耗时版本的快照。
3. 高境界装备封存一条词条后反复重铸，固定复现第九次出现 **5 条**，原样导入返回“词条条数无效”。代码先抽满上限，再把锁定词条插入；当抽中集合不包含锁定 ID 时超过上限。低境界也可能超过该境设计条数。

依据：v1.3 第 8 节存档要求；v1.4 R59 明确要求合法风任务通过校验；v1.6 每件 1～4 条及封存规则。位置：`engine.ts:689–692 / 891 / 3086 / 3321`。

建议：补齐合法物品枚举；给任务保存并验证实际耗时与规则版本；封存词条占用生成名额。复验必须通过“真实动作 → 导出 → 导入 → 刷新/重启”，保留收益、在途状态、实例和词条。

### P1-02 坏档可以覆盖存档、使页面崩溃，委托矛盾状态可以重领奖

**已完成脚本与实际浏览器复现。** `marrowHistory: [null]` 被接受导入，人物页渲染历史时访问空对象导致客户端崩溃，刷新后仍崩溃。导入前备份存在，但人物页里的恢复按钮随页面一起不可访问，本轮通过独立测试库恢复才继续检查。截图见证据 04。

同时接受重复灵根 `['金','金']` 与不属于人物的 `resonance='雷'`；导入入口没有校验命盘及洗髓历史结构。委托校验只检查单字段类型：把已领奖历史复制为当前 `ready` 委托，保留原领奖信息，导入仍成功，并可再领一次。奖励数值也没有与规则版本、目标和领取事实交叉验证。

依据：AGENTS.md 坏档/结构校验底线，v1.4 R62、v1.8 第 3 节第 5 条与验收清单。位置：`engine.ts:3203–3257 / 3460–3525`；`renwu/page.tsx:176`。

建议：补完整结构及关系校验，当前版本必需字段不可作为“旧档缺省”直接放行；提交前完成全部验证，失败保留原档；读取时提供可操作的故障恢复入口。跨日同类型委托 ID 可能相同，防重领奖应使用包含接取日期/实例身份的标识，不能简单禁止所有同类型历史。

### P1-03 一级至五级炼器台都被页面判为“尚未建造”

**已在浏览器复现。** 一级炼器台角色进入背包，看不到精钢剑等任何炼制按钮，显示“需先建造炼器台方可炼器”。条件使用 `state.forge < CONFIG.forge.levels.length`，扩充成六级以后变成必须满级才开放整个系统。截图见证据 03。

这会挡住早中期装备成长，也可能生成玩家无法在页面完成的炼器委托。依据：v1.0 原一级炼器、v1.3 第 6.4 节明确保留一级功能。位置：`beibao/page.tsx:194`。

建议：总入口以是否建造判断；每个配方分别显示需要的炼器台等级、境界与材料。复验 0/1/2/5/6 级入口及对应委托完成。

### P1-04 成长的境界门槛、配方建筑门槛和部分升级费用漏实现

**边界动作已复现，费用遗漏由配置和扣费代码确认。** 给合成角色足够材料后，炼气一层可把修炼室升到八级、青云诀从三重升到四重；筑基一层可把藏经阁升满七级；炼虚二层使用一级炼器台即可炼制应需更高炼器台的虚空刃。

引擎建筑升级只有满级与费用判断，藏经阁/炼器台所有升级都沿用“筑基一层”；新装备没有对应炼器台等级判断，淬炼没有分段建筑/境界门槛。收益丹也漏掉凡品筑基门槛。炼丹炉 Lv4/5/6 仅扣灵石，漏扣 PRD 规定的残页 **100/600/2500**。

依据：v1.3 第 3、5、6 节和第 9 节验收；不存在已确认取消这些规则的决策。位置：`engine.ts:1514 / 1609 / 1629 / 1647 / 1673 / 1698 / 1762`，`config.ts` 建筑/配方配置。

建议：将逐级开放条件与所有资源费用放入统一规则，展示、预览和执行共用；逐档验证境界不足/资源不足不扣费，满足后才升级。增加规则前需保留已经合法获得的旧等级及物品，不能直接删除玩家进度。

### P1-05 日期回拨可重新生成每日委托并重复获奖

**无需修改委托数据，使用正常动作已复现。** 10 月 2 日接取、挑战、领奖；10 月 3 日再完成；把时间回到 10 月 2 日，仍能重新生成并领奖，历史形成“2 日、3 日、2 日”三次记录。

`ensureCommission` 只检查日期是否相等，日期向后跳也重置候选。`ensureDaily`、`ensureSecretRealm` 有相同回拨重置模式；普通收益结算里的非负时间处理并不能保护每日额度。

依据：v1.8 验收明确“时间回拨不能刷新额度”。位置：`engine.ts:340 / 346 / 474`。

建议：持久化已结算日期高水位及接取/领奖实例身份，回拨不刷新额度；分别复验委托、重复历练、秘境和服丹的日限制。完全离线存档无法提供服务端级防作弊，但至少应实现 PRD 要求的回拨保护。

### P1-06 模型失败响应不记费用，预算限制与重试时间不可靠

**费用遗漏通过无网络假响应复现。** 模拟两次厂商响应均带 `usage`（每次 1000 输入、200 输出 token），但正文无法解析，最终返回模板，实际本地月度记账为 **0**。这是失败场景模拟，不是成功模型验证；另一次真实成功冒烟已独立执行。

`record_usage` 位于解析和审核通过之后，解析/审核被拒的付费调用被漏记。预算只在外层重试前检查一次；并发请求也没有预留费用。费用文件损坏时 `_load()` 返回空账本，会失去已有额度。SDK 初始化未指定 `max_retries`，本地 SDK 默认重试 2 次，与业务两轮叠加；前端 4 秒取消，后端可能继续重试消耗费用。

依据：AGENTS.md 费用约束和模型失败有限重试；v1.0.2 月度预算熔断。位置：`backend/app/services/llm.py:76–130`、`budget.py:20–75`；`frontend/src/lib/api.ts:43`。后几项为代码确认的保护缺口，未故意制造真实并发费用或网络超时收费。

建议：收到 usage 即计费；对每次尝试预留并结算费用，坏账本显式失败或安全降级；统一 SDK 与业务重试层，协调端到端超时。增加失败/审核拒绝/重试/并发/坏文件验证。

## 6. 开发复现入口

前端脚本：[reproduce.ts](./reproduce.ts)。在 `frontend` 执行：

```bash
node node_modules/vite-node/vite-node.mjs ../docs/阶段文档/全局审查-2026-10-01/reproduce.ts
```

脚本打印正常导入失败、时间回拨领奖、装备重复、锁词条溢出、门槛遗漏、坏档接受及旧式灵根迁移等结果。`crossDayAllowsAnother` 只是观察跨日任务完成后还能接当日任务，不单独判为漏洞；已确认漏洞以 `rollbackCommission` 为准。

```bash
backend/.venv/bin/python docs/阶段文档/全局审查-2026-10-01/reproduce_backend.py
```

脚本使用临时费用文件及假 SDK 响应，不发送请求、不污染真实账本。所有复现输出仅供技术核对；产品证据包不存命令日志。
