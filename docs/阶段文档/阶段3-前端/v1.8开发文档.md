# v1.8 开发文档：战前战术 + 山河委托

> 配套 PRD：`docs/PRD/PRD-修仙放置游戏-v1.8-战术与山河委托-待确认.md`。产品经理已确认：按推荐完整开发（A 战前战术 + B 山河委托，两段分别验收，先 A 后 B）。本轮为原创玩法，沿用现有地图、资源与本地存档，不新增云费用、AI 调用或新货币。

## 1. 范围

- **A 战前战术**：已普通首胜的**挑战难度**战斗前，选「常法／破势／守拙」，先看胜负预估再出战；战后摘要写明所选战术与真实影响；旧档默认常法。
- **B 山河委托**：历练页在普通首胜后显示「山河委托」，每日两件候选接一件，完成后两种等价值奖励选一种，固定人物递交并留一句后续回应。

**不改变**：普通首通、秘境、天劫、长任务的规则；每日重复奖励额度、际遇触发；伤害公式与敌人强度；六至八周节奏目标。不做自由剧情、AI 自主判定、手动逐回合、宗门/NPC 好感/交易/新货币。

## 2. 数据模型（schema v17 → v18）

### 2.1 战前战术

`types.ts` 增：

```ts
export type TacticId = "normal" | "break" | "guard";
```

`LastBattle` 增 `tactic: TacticId`（挑战战记录所选战术；普通/秘境固定 "normal"）。

### 2.2 山河委托

```ts
export type CommissionKind = "battle" | "craft";
export type CommissionStatus = "accepted" | "ready" | "claimed";

export interface Commission {
  id: string;
  kind: CommissionKind;
  title: string;
  mapId?: MapId;            // battle
  nodeId?: string;
  difficulty?: BattleDifficulty;
  action?: string;          // craft（如 craftEquipment / craftPill / upgradeBuilding / upgradeTechnique / buildLibrary / buildForge / useGainPill）
  actionParam?: string;
  target: number;           // 需完成次数（本版固定 1）
  progress: number;
  rewardA: Resources;
  rewardB: Resources;
  status: CommissionStatus;
  rewardChoice?: "a" | "b";
  claimedAt?: number;
  response?: string;        // 固定人物后续回应
}

export interface CommissionState {
  date: string;             // 候选生成日期 YYYY-MM-DD
  candidates: Commission[]; // 2 个当日候选（未接取）
  active: Commission | null; // 已接取（accepted / ready）
  history: Commission[];    // 已领奖（含回应）
}
```

`SaveState` 增 `commission: CommissionState`。

## 3. 配置（config.ts）

### 3.1 战术

```ts
tactics: {
  normal: { name: "常法", damageMult: 1, takenMult: 1, note: "沿用既有攻守" },
  break:  { name: "破势", damageMult: 1.25, takenMult: 1.35, note: "提高输出、承伤更重" },
  guard:  { name: "守拙", damageMult: 0.78, takenMult: 0.70, note: "降低输出、提升生存" },
}
```

倍率为首轮值，用第 8 节模拟测试验证「破势适合限回合、守拙适合高伤敌人、无唯一最优」后定稿；若达不到则调整参数或缩小开放范围。

### 3.2 委托

```ts
commission: {
  fixedNpcName: "青崖",
  dailyCandidates: 2,
  rewardShare: 0.15,       // 委托奖励 ≈ 当前日产出 × 0.15（首轮保守值，待 6～8 周节奏模拟定稿）
  battleTargetMinCleared: 1,
}
```

## 4. 引擎改动（engine.ts）

### 4.1 A 战前战术

- `predictFight(state, mapId, nodeId, difficulty, tactic = "normal")`、`fightNode(state, nowMs, mapId, nodeId, difficulty, tactic = "normal")` 增 `tactic` 参数；仅 `difficulty === "challenge"` 时应用倍率（`normal` 恒为 1×）。
- 应用方式：把 `tacticCfg.damageMult/takenMult` 乘进 `runBattle` 的 `dmgMult/takenMult` 入参，不改 `runBattle` 本身。
- `fightNode` 构造 `lastBattle` 时写 `tactic`；`buildBattleReport` 增 `tactic` 字段。
- 挑战战败不扣每日重复奖励额度（现有逻辑已如此，保留），获胜奖励/掉落/额度/际遇沿用。

### 4.2 B 山河委托

- `settle` 内调用 `ensureCommission(s, nowMs)`：跨日重新生成 2 候选（`commission.date !== today`），不清掉已接取的 `active`。
- `generateCandidates(s)` 生成两件当前可完成的候选：
  - **战斗候选**：从已 `cleared` 的节点挑一个（优先当前地图）→「在【地图·节点】赢得一场挑战（挑战难度）」，`difficulty="challenge"`。
  - **制作候选**：按优先级挑一个已解锁动作（炼器台→炼制装备、炼丹炉→炼制护劫丹、建筑可升级→升级建筑、功法可升级→精进功法、有收益丹→服用、否则回退为「完成 1 次历练胜利」），只选结构上当前可完成的动作。
- 委托动作：`acceptCommission(state, nowMs, id)`（从候选接取一件，写入 `active`）、`claimCommission(state, nowMs, choice)`（奖励两选一、入账、记修仙录、写入 `history` 并附 `response`）、`commissionProgress(s, kind, match)` 助手。
- 进度钩子：在 `fightNode`（胜利）、`craftEquipment`、`craftPill`、`upgradeBuilding`、`upgradeTechnique`、`buildLibrary`、`buildForge`、`useGainPill` 成功路径调用 `commissionProgress`，命中 `active` 目标则 `progress+1`，达到 `target` 转 `ready`。
- 奖励：以 `productionBreakdown` 的日产出为基准，`rewardA`（战斗向）与 `rewardB`（资源向）各约 `rewardShare × 日产出` 的价值，两选一等价值。
- 固定人物「青崖」只写固定文案（递交、领奖回应、历史回看），不自由聊天、不决定目标/胜负/奖励；AI 不参与。

### 4.3 迁移与校验

- `SCHEMA_VERSION` 17 → 18。
- `createGame` 默认 `commission: { date: today, candidates: [], active: null, history: [] }`。
- `migrateSave` 补 `commission` 默认、`lastBattle.tactic` 默认 "normal"（旧档最近一战视为常法）。
- `importSave` 增 `validateCommission` 与 `lastBattle.tactic` 校验：候选/进行中/历史状态、奖励字段、进度与目标、日期、奖励选择均合法；无效新字段拒绝导入（现档不变）。`candidates.length <= dailyCandidates`。

## 7. 测试

新增 `v1.8-tactics.test.ts` 与 `v1.8-commission.test.ts`（或并入现有）：

**A 战前战术**
1. 挑战难度三种战术切换后预估变化；`normal` 难度战术不生效（强制常法）。
2. 同一场战斗 `tactic="break"` 与 `tactic="guard"` 的实际结算不同，且 `lastBattle.tactic` 正确。
3. 挑战战败不扣每日重复奖励额度；获胜奖励/额度/际遇沿用。
4. 用代表敌人模拟：破势回合数 ≤ 常法（限回合场景），守拙承伤/存活优于破势（高伤场景），无唯一最优；记录数值。

**B 山河委托**
1. 跨日生成两件当前可完成候选；接取一件后 `active` 正确、候选清空。
2. 战斗候选：在目标节点挑战获胜 → `progress` 到 `target` → `ready`；失败不推进。
3. 制作候选：完成对应制作/养成动作 → `ready`。
4. `claimCommission` 两选一：入账、修仙录记录、写入 `history`、`active` 清空；重复点击/双标签不重复领奖。
5. 跨日保留已接取 `active`；旧档迁移 `commission` 默认空；坏档拒绝导入。

## 8. 验收（对应 PRD 第 6 节）

- A：挑战节点三战术可选、预估变化、战报如实写战术与实际结果；至少一场战斗通过换战术改变结果或 12 回合是否达标；普通/秘境/天劫/长任务/旧档保持原规则；桌面与 390px 走通。
- B：早/中/后期各生成两件当前可完成、目标不同的委托；领奖只一次、两选一有取舍；跨日/刷新/重启/导出导入/双标签/坏档不丢进度、不重复领奖；奖励不使 6～8 周目标失控（无法模拟或未真人验证时写「待验」）。
- 闸门：前端自动测试 + typecheck/Lint/build 通过；桌面与 390px 浏览器闭环；存档恢复；密钥排除；README 与项目状态更新；证据包入 `docs/evidence/`。真实模型冒烟沿用现有阶段 3 总闸门记录（本轮无新增模型调用）。
