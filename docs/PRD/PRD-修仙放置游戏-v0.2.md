# 「青云修仙录」产品需求文档 v0.2

> 文档状态：需求优化稿；本次只更新 PRD，不启动开发。  
> 来源：`PRD-修仙放置游戏.md` 初版及其已确认的 8 项约束。  
> 版本原则：保留已确认的产品方向；本版新增的内容数量、数值和时长均为首轮试玩基线，开发时通过配置调整，不视为用户已确认的最终平衡值。
> 历史版本说明：本稿当时的“四界二十一境”长期构想已由产品经理 2026-09-27 确认的[二十境、每境十层总纲](PRD-修仙放置游戏-v1.2-二十境.md)取代；下文 MVP 内容量、规则和验收记录仍按当时版本理解。

## 1. 本版决策摘要

| 事项 | v0.2 决策 |
|---|---|
| 产品形态 | 移动端优先的单机网页文字放置游戏，五个主入口：洞府、修炼、历练、背包、人物。 |
| 首版终点 | 从炼气一层推进到筑基一层，完成一次可预判、可准备、失败可恢复的天劫。旧稿曾设四界二十一境；现行长期目标为二十境、每境十层，不属于本 MVP 内容量。 |
| AI 范围 | AI 际遇文案进入 MVP；游戏规则、选项、分支和奖励均由确定性引擎决定。AI 不可用时使用同一事件的模板文案。 |
| 存档归属 | 存档留在浏览器本地，支持导出和导入。后端只代理 AI 请求，不保存玩家进度，不设账号。 |
| 离线结算 | 玩家重新进入游戏时按时间差结算，单次最多 12 小时；不依赖常驻定时任务。 |
| 商业与内容 | MVP 免费、无内购、无 PVP；文字严格半文半白，可适度引典籍，避免血腥暴力描写。 |

### 1.1 相对初版的主要调整

1. 把首版从“全部系统先做一遍”收为一段完整的筑基体验，并给出明确内容量。
2. 统一星象、轮回、建筑数量等在优先级表和版本规划中的冲突。
3. 明确本地存档、离线结算、跨标签页和导入导出的行为。
4. 将 AI 事件改为“引擎先定事实，AI 再写文字”，增加结构校验、超时和模板降级。
5. 增加玩法规则、首轮参数、验收场景与指标口径。

## 2. 产品目标与体验

### 2.1 目标玩家

喜欢修仙题材、文字氛围和渐进成长的放置玩家。玩家可以短时上线做决策，也能离线积累资源；不要求持续盯屏。

### 2.2 核心体验

**收取修行所得 → 选择突破或历练 → 击败节点并镇压取得持续产出 → 升级洞府、功法与装备 → 看清劫势并准备渡劫 → 筑基。**

数值增长给持续反馈；渡劫前的准备和风险预览提供关键决策；与人物状态相关的际遇文字提供差异化。首版的差异化是**个性化际遇**，长篇修仙录传记和 NPC 对话分别在后续版本实现。

### 2.3 已确认约束

- 平台为网页，移动端优先；首版单机，无账号、PVP、内购。
- AI 叙事进入 MVP，但 AI 故障不得阻断游戏。
- 数值先提供可玩基线并可配置，后续通过试玩调优。
- 文案采用半文半白，典籍引用须准确且自然；不得出现血腥猎奇内容。
- 观察平均有效游玩时长与留存，但不以延长无意义等待为设计目标。

## 4. 玩家流程与核心规则

### 4.1 首次进入

玩家填写姓名，选择五行灵根。五种灵根在 MVP 中享有相同的修炼基础值，类型用于人物设定与际遇文案，不产生隐藏的强弱差距。初始人物获得一件基础装备及引导所需资源。

引导只要求完成四件事：领取挂机收益、完成首次小进阶、击败并镇压首个历练节点、查看一次劫势预览。之后不强制引导。

### 4.2 修为、灵气与突破

- 修为和灵气按实际经过时间累积；前台显示每秒刷新，后台标签页和重新打开时用时间差补算，不依赖逐秒定时器的准确性。
- 小进阶需要同时满足修为、灵气门槛，由玩家手动确认；成功率在 MVP 为 100%，扣除表中消耗。修为不会“自动突破”。
- 炼气圆满后可查看劫势、装备及护劫丹，再手动选择渡劫。达到门槛不会自动进入天劫。
- 各项消耗、产出、倍率与上限集中在配置表；展示值和实际计算值采用同一来源。不得仅改界面文字而未同步规则。

首轮试玩参数如下，数值均为可调基线：

| 参数 | 初值 |
|---|---:|
| 基础修为产出 | 1 点/秒 |
| 基础灵气产出 | 0.25 点/秒 |
| 炼气一层→二层 | 120 修为、20 灵气 |
| 二层→三层 | 300 修为、50 灵气 |
| 三层→圆满 | 700 修为、100 灵气 |
| 圆满→筑基渡劫门槛 | 1500 修为、200 灵气 |
| 离线单次结算上限 | 12 小时 |

以上门槛旨在形成约 45～75 分钟的首次筑基体验目标，包含历练所得与洞府升级；实际是否达到目标以模拟和试玩验证。每次点击确认渡劫均消耗一次门槛资源；同一次尝试因刷新恢复时不得再次扣除。失败后的结果另按 4.5 处理。

### 4.3 资源经济

| 资源 | MVP 来源 | MVP 用途 |
|---|---|---|
| 修为 | 时间产出、首次通关、战斗胜利 | 小进阶与渡劫门槛 |
| 灵气 | 时间产出、聚灵阵 | 小进阶与渡劫门槛 |
| 灵石 | 首次通关、镇压产出、际遇分支 | 建筑升级、护劫丹炼制 |
| 灵草 | 灵田、历练节点 | 护劫丹炼制 |
| 残页 | 指定节点首通及重复战斗、少量际遇分支 | 主修功法升级 |

每种资源至少有一个可预期来源和一个明确用途。战斗与际遇奖励由配置表按事件 ID 和分支 ID 给出；AI 文案不得增减奖励。

### 4.4 历练、战斗与镇压

- 地图节点按顺序解锁；首次胜利获得固定首通奖励，后续重复战斗只得常规奖励。未达到境界门槛的节点不可进入，界面说明解锁条件。
- MVP 战斗为自动回合制：玩家先手，双方交替攻击；单次伤害 `max(1, 攻击－防御)`，气血降至 0 即结束。首版无暴击、随机词条或主动技能；相同状态与节点的结果可复现。
- 战败不掉装备、不倒退境界，也不额外扣除修为；本次挑战不获得胜利奖励。战报指出造成失败的属性短板，并提供可执行的提升路径。
- 首通地图内节点后可将其中一个已通关节点设为该图镇压目标。同一地图同时只能镇压一个节点；切换目标后按新节点产出率结算未来收益，不重算过去收益。
- 镇压产出与修炼产出一样按时间差结算，受相同的 12 小时离线时长上限约束。妖气复聚和镇压失效属于 V1.1。

### 4.5 天劫

MVP 的第一次天劫固定为五波。基础伤害按最大气血的 `[20%, 25%, 30%, 35%, 40%]` 计算；装备和功法提供的护劫减伤先作用于每波伤害，减伤总和上限为 40%。预置的一枚护劫丹在第三波结束后恢复 30% 最大气血，且只消耗一次。最终每波伤害向上取整，恢复不得超过最大气血。

渡劫页面必须展示当前气血、减伤来源、是否预置丹药、五波预计伤害和预计结果。首次天劫不掷隐藏随机数，因此玩家能依据预览做准备。后续版本再引入劫势变化。

- **成功：**进入筑基一层，记录完整五波战报，解锁后续内容提示。
- **失败：**停留炼气圆满；已扣除的渡劫门槛不退还；消耗预置丹药；不损失装备、建筑、镇压节点或既有境界。界面明确提示重新积累门槛及推荐准备方式。
- **退出或刷新：**点击渡劫时先保存一次待结算事件；重新进入时按保存的事件 ID 完成同一次结算，不得重复扣费、重复用药或重复晋级。

### 4.6 洞府、功法与装备

- 修炼室提高修为产出；聚灵阵提高灵气产出；灵田按时间产灵草；炼丹炉消耗灵草和灵石炼制护劫丹。建筑最高 3 级，升级立即生效；升级前按旧速率结算至当前时刻，之后按新速率计算。
- 主修位只能装备一本功法。两本功法分别偏向修炼速度和护劫减伤，使用残页升级，最高 3 级。切换主修后同样先结算旧速率。
- 三个装备位为武器、护甲、佩饰。装备来自固定节点首通奖励；同类只能装备一件，切换即时更新属性。装备不会被 AI 命名或生成随机属性。
- 所有升级界面展示当前效果、升级后效果与资源消耗；资源不足时按钮不可执行并指出缺少什么。

## 5. AI 际遇的产品与数据契约

### 5.1 触发与体验

首版有 3 种固定事件原型，每种包含 2 个预设选项及确定的分支结果。首次到达指定节点必触发一次引导事件；之后战斗结束时按配置概率触发，同一角色每天最多触发 3 次需要 AI 请求的际遇。具体概率由配置决定，默认 20%。离线结算不触发新际遇，以免玩家回来时堆积待选事件。

事件进入待选择状态时，引擎已锁定事件 ID、选项 ID、分支效果和奖励。界面最多等待 AI 文案 4 秒；超时、接口错误、结构不合格或审核不通过时立即显示对应模板，玩家始终能继续游戏。奖励在玩家选择后即时由本地引擎结算，不等待 AI。

### 5.2 输入、输出与校验

后端只接收写作所需的最少上下文：事件原型 ID、姓名或可替代称呼、灵根、境界、地图 ID、最近两条修行摘要和预设选项含义。不得向模型发送完整存档、导出文件或浏览器标识。

AI 返回的数据只允许包含：`event_id`、`title`、`body`、按既定 `option_id` 对应的 `option_text`。引擎从配置表读取 `option_id → result_id → reward`，AI 响应中的奖励、概率、属性和数值字段一律不接收。校验须覆盖：事件 ID 一致、选项 ID 集合完全一致、长度范围、占位符合法、不得承诺与配置冲突的结果、内容安全与文风。原始模型文本不得直接拼入 HTML。

即使结构合法，若 AI 文案暗示了与分支不符的收益或因果，也必须使用模板。提示词和审核只辅助保证质量；规则边界以固定事件配置和输出校验为准。

### 5.3 内容规范与成本边界

- 叙事文案半文半白且易读；可引典籍，但不得杜撰引文出处。数值、规则和失败原因使用清楚的白话说明。
- 斗法、失败与陨落使用克制、写意的表达，不写血腥细节；不生成侮辱性或越界内容。
- 模板库覆盖全部 3 种事件及其 6 个分支结果；AI 关闭或代理服务离线时仍可完成全部首版流程。
- 后端保存模型密钥，配置请求超时与限流。匿名访问按服务端可用的限流维度控制调用量；本地每日次数限制仅用于体验节奏，不作为费用防护。
- 人物的“修行记录”由引擎写入事实摘要，MVP 不调用 `write_biography`；AI 长篇传记在 V1.1 实现。

## 6. 存档、离线与部署

### 6.1 状态归属

游戏状态与规则配置由网页客户端管理，存档写入浏览器 IndexedDB。AI 后端是无玩家存档的代理服务；断网或服务不可用时照常使用模板事件。模型密钥只存后端环境变量，绝不打包到前端。

存档至少包含：`schemaVersion`、角色 ID、角色资料、资源、境界、功法/装备/建筑等级、地图与镇压状态、已触发事件、待结算事件、最近修行记录、`lastSettledAt`、修订号。所有会改变资源或进度的操作应作为一个事务提交，避免刷新时出现“扣费成功但升级失败”。

### 6.2 时间结算

每次读取并操作存档前，先计算 `delta = clamp(当前时间－lastSettledAt, 0, 12 小时)`，按本次结算前的产出率增加修为、灵气、灵草与镇压收益，再在同一事务中将 `lastSettledAt` 更新为 `max(原 lastSettledAt, 当前时间)`。前台展示可高频刷新，但数值结算以状态事务为准。游戏关闭期间不运行定时任务，也不产生战斗或 AI 事件。

负时间差按 0 处理；超出上限只结算 12 小时并提示上限。单机本地存档不承诺防作弊，但不得因系统时间回拨、刷新或多标签页造成负收益或重复结算。多标签页采用单写入者机制或等效事务与修订号校验；其他标签页只读并提示正在另一标签页运行。

### 6.3 导出、导入与重置

- 导出为带版本号的 JSON 文件，不含后端密钥或调用凭证。
- 导入先校验结构、必需字段、数值范围和版本；可迁移时先备份当前存档再迁移；不兼容时拒绝并说明原因，不覆盖原档。
- 手动重置需明确二次确认，并允许事先导出。MVP 重置就是新开一局，不保留道果；轮回规则在二期单独实现。

## 7. 体验目标、埋点与验收

### 7.1 首轮体验目标

以下用于试玩调参，不代表市场表现承诺：

| 指标 | 定义 | 首轮目标 |
|---|---|---|
| 首次筑基历时 | 连续试玩样本从创建角色到第一次天劫成功的实际经过时间，包含期间挂机等待；跨日回访样本单独观察。 | 45～75 分钟的典型路线。 |
| 首次渡劫可理解性 | 不看外部攻略时，玩家能说出失败原因和下一步准备。 | 试玩访谈中多数玩家能回答。 |
| 核心流程完整率 | 新手从角色创建完成到首个节点镇压成功的比例。 | 用于识别卡点，首测后定阈值。 |
| 平均有效游玩时长 | 前台可见且有输入或状态查看活动的时长；后台挂机不计入。 | 基线观察，首测后定阈值。 |
| D1/D7 留存 | 首次进入后的次日/第七日再次打开且发生有效活动的匿名角色占比。 | 基线观察，首测后定阈值。 |

单机无账号时，留存仅能按本地匿名角色或自愿开启的匿名统计估算；清除浏览器数据、换设备与跨浏览器会打断身份。若不启用匿名上报，只能在本机查看体验数据，不能声称已测得整体 D1/D7。统计开关、数据用途与是否上报需在产品设置中明示。

### 7.2 必须通过的验收场景

1. **完整首玩：**新角色可以完成小进阶、首个节点首通与镇压、建筑升级、功法或装备调整、第一次渡劫，并到达筑基一层；五个入口在窄屏下均可操作。
2. **经济一致：**相同初始存档、操作序列与经过时间产生相同资源及战斗结果；每次扣费都与获得的效果一起提交。
3. **离线结算：**关闭 2 小时后收益按 2 小时计算；关闭 14 小时后按 12 小时计算；重复刷新和多标签页不会再次领取同一时段收益。
4. **天劫恢复：**预览值与实际五波计算一致；失败后角色仍可重新积累资源；渡劫过程中刷新不会双重扣费或重复晋级。
5. **AI 降级：**模型超时、断网、返回错误选项 ID、返回违规文字或暗示错误奖励时均显示模板；玩家仍可选择并领取引擎规定的奖励。
6. **存档安全：**导出后导入可恢复同一进度；损坏或不兼容文件不覆盖当前存档；手动重置后是新档，不能误称轮回。
7. **文案质量：**事件模板和 AI 输出均符合半文半白、准确引用、易读及内容尺度要求；规则提示使用清楚的白话。

## 8. 技术边界与实施顺序

游戏引擎使用可复现的纯状态转换处理收益、战斗、分支奖励与天劫；界面负责展示和发起命令；本地存档负责持久化；AI 代理只提供受校验的文案。建议先做配置和状态机，再做存档与离线、五入口最小界面，最后接 AI 生成和模板降级。模型供应商和前端框架在开发时选择，不改变本 PRD 的行为要求。

仓库的 `scaffold/agent.py` 与 s01～s17 可作为 AI 代理的参考实现。MVP 只有一类生成任务，不要求把记忆系统、定时调度、目标闭环或完整集成 Harness 全部引入运行时。需要保留的是结构校验、内容审核、超时、限流、日志和降级能力。离线收益、地图复聚与星象轮转属于游戏状态规则，不交给 Agent 的定时任务。

## 9. 待试玩验证的参数与后续决策

- 首次筑基的真实耗时、最优路线与失败后的恢复时间；若目标区间偏离，先调整配置，再决定是否改规则。
- 两本功法与三装备位是否形成可理解的选择，避免存在明显唯一正确答案。
- AI 际遇相较模板是否提升阅读兴趣；分别记录触发、成功展示、降级和选择完成的次数，并通过试玩访谈判断文字是否易读。
- 浏览器本地存档容量与修行记录保留条数；超过上限时只归档旧记录，不丢失进度。
- 长期世界观、星象、九装备位、七建筑、传记、社交与轮回的扩展顺序，依据首版试玩结果再排期。
